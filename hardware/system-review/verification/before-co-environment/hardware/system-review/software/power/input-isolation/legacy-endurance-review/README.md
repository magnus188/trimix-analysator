# Legacy charger endurance correction

Status: correction implemented; focused digital checks passed. Full firmware integration is recorded separately. No physical charging test was performed.

An ASan/UBSan test of the actual ESP power worker reproduced a stable legacy DCP entering dark charging standby and invoking KILL at virtual time **32,549 ms**. The old BC capability expired after 30 seconds; periodic redetection then looked like source loss to standby. `before.log` retains that failure. The independent `repro.cpp` changes only the test boundary and duration; production files were unchanged for that failing run. Exact original BC driver/header bytes were reconstructed and verified against their captured pre-change SHA-256 values under `before/`. This is an extension of the test coverage, not a physical measurement.

The [PI3USB9201 datasheet, Rev 3-2, p8](https://www.diodes.com/datasheet/download/PI3USB9201.pdf) specifies detection on entering ATTACHED.SNK and clearing detection/powering down when leaving it. Its classification registers clear on read. We therefore retain a classification for a continuously verified attachment. The original `observed_ms` never advances. Separate `validated_ms` records exact control-register readback with the caller's freshly polled CC generation. A **3-second maximum health-check gap**, including read latency, invalidates the result. This deadline is an application choice, not a manufacturer guarantee.

This also avoids periodic HIZ/charge-enable cycling. [BQ25895 Rev C, §8.2.7.1](https://www.ti.com/lit/ds/symlink/bq25895.pdf) allows toggling charge enable to initiate another cycle after completion. We do not assume that repeated cycling preserves termination or safety-timer history. The software tests check that a stable attachment does not repeat these writes; they do not simulate the real timer or cell chemistry.

The same source generation alone is insufficient. Coherent CC state, expected controller identity/configuration, fresh charger status, hardware latch feedback and normal maintenance guards remain required by the combined policy. Detach/replug, invalid CC, detector reset, failed reads, missed health interval and stale generations revoke permission. Only a new explicit detection cycle can restore a discarded result. Default SDP and unknown/proprietary sources remain in verified HIZ.

Focused tests now cover six virtual hours each for DCP and CDP, with no repeated detection, HIZ exit or charge-enable edge after stable standby begins. Further actual-worker scenarios inject a missed four-second interval, observed detach, a sticky replug event with the same final CC state, and detector-control reset after two minutes. All revoke permission and isolate input before shutdown. Driver tests retain the original observation timestamp, exercise deadline crossings during I2C reads, clock wrap, bus/configuration faults and stale-cycle rejection.

`../evidence/receipt.json` is the source-bound current suite: **460 reported ASan/UBSan assertions**, 45 recorded commands, 101 scoped inputs unchanged, four worker maintenance races plus concurrent backlight TSan checks. The six-hour runs use a virtual clock and boundary fakes; those hours are not physical runtime, and assertion counts are not independent safety proofs. Production charging remains CommissioningInhibited with J104 OPEN. Whole-board current, hot-plug, cold recovery, electrical detach timing, actual safety timers and charging remain unqualified.

An independent boundary review found and corrected two further CC interrupt races: an event hidden under the initial sticky bit, and a new event erased by an unnecessary final W1C. The correction acknowledges CC before a new BC cycle and makes the post-result legacy barrier read-only. Three additional actual-worker boundary tests and no-post-result-ACK assertions now run in the same receipt. Details, intentional failing archived-policy controls and source hashes are in [independent-review.md](independent-review.md) and `independent-review.json`. Previous full integration evidence is preserved under `hardware/system-review/verification/before-bc-attachment-edge-fix/`; current complete firmware builds remain governed by the parent integration receipt.
